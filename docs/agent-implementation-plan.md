# Agent 能力实施方案

## 1. 背景

当前系统已经具备以下基础能力：

- 微信群消息入站、出站与桥接
- 普通 LLM 对话
- FAQ / 知识库 / 记忆 / 回复风格 / 积分 / 审核 / 复读机等插件
- OpenAI 协议下的 `tools / tool_calls` 基础协议支持

但现阶段 `RouteType.AGENT` 仍然只是复用普通 `LLMCapabilityEngine`，没有真正接上工具执行层。因此机器人虽然能“聊天”，但还不能像群聊 Agent 一样读取当前群的公开信息、成员列表、最近消息、插件状态等结构化数据。

直接结果是：

- 群聊问“这个群有哪些人”“刚才谁说了 xxx”“这个群最近活跃吗”时，模型只能靠上下文猜
- 无法稳定回答基于当前群真实数据的问题
- 无法把“群事实查询”和“普通闲聊”明显区分开

本方案目标是把当前平台演进成“具备群聊上下文查询能力的 Agent Console”，并按三期逐步落地。

## 2. 总目标

将当前群聊机器人从“普通 LLM 回复器”升级为“可调用群数据工具的 Agent”。

核心能力包括：

- 识别当前问题是否需要查询群内真实数据
- 在当前会话范围内调用白名单工具
- 将工具返回结果组织成符合群聊风格的短回复
- 保持现有插件体系、命令体系、积分/审核等既有逻辑不被 Agent 干扰

## 3. 非目标

以下内容不在初期目标内：

- 通用 autonomous agent，自主规划复杂长链任务
- 跨群查询
- 调用任意外部网络服务
- 高权限群管理动作，例如踢人、改群名、发公告
- 把所有插件逻辑都立即改成 tool 化

第一阶段只做“当前群公开信息查询 Agent”。

## 4. 现状评估

### 4.1 已有基础

- LLM Provider 已支持 OpenAI 协议的 `tools`
- 数据结构中已有 `ToolSchema`、`ToolCall`
- wxbot 已有群列表、群成员、成员事件、历史消息读取入口
- 命令中心已经能稳定拦截 `/xxx`
- 插件架构已经支持扩展 capability engine

### 4.2 当前缺失

- 缺少真正的 `AgentCapabilityEngine`
- 缺少统一的工具注册与执行层
- 缺少“何时从 LLM 切换到 AGENT”的路由规则
- 缺少工具调用审计
- 缺少前端对 Agent 能力范围的可视化控制

## 5. 总体架构设计

建议采用“命令 + Agent 工具”的双层设计。

### 5.1 命令层

适合确定性强、响应格式固定的能力：

- `/群成员`
- `/群资料`
- `/积分榜`
- `/签到`

特点：

- 稳定
- 可控
- 不依赖模型发挥
- 适合后台运维和固定功能

### 5.2 Agent 工具层

适合自然语言群事实查询：

- “这个群有哪些人”
- “群里谁最活跃”
- “刚才谁提到了画图”
- “本群最近有人退群吗”

特点：

- 问法自然
- 模型负责理解问题意图
- 工具负责查询真实数据
- 最终回复仍保留群聊风格与 persona 风格

### 5.3 设计原则

- 命令优先于 Agent
- 确定性插件优先于 Agent
- Agent 仅允许访问当前会话
- 工具调用有白名单和数量上限
- 工具返回数据必须裁剪，避免大上下文爆炸

## 6. 路由优先级建议

群聊消息建议按如下顺序判断：

1. 自身消息 / 审计消息 / 非文本消息：按现有逻辑处理
2. `/` 开头命令：优先走命令中心
3. 被积分、审核、复读机、签到等插件命中：优先走对应插件
4. `@机器人` 且命中“群成员 / 群资料 / 谁 / 本群 / 大家 / 最近谁 / 群里有谁”等 Agent 意图：走 `RouteType.AGENT`
5. `@机器人` 普通聊天：走 `RouteType.LLM`
6. 非 `@` 且非命令：由现有群聊回复策略决定是否忽略

这样可以保证：

- Agent 不抢命令
- Agent 不抢插件
- Agent 只处理真正需要查群事实的问题

## 7. 一期：够用版

### 7.1 目标

实现最小可用的“群资料查询 Agent”。

### 7.2 能力范围

- 新增真正的 `AgentCapabilityEngine`
- 接 `list_group_members`
- 接 `get_group_info`
- 只在 `@机器人` 且命中群信息类意图时路由到 AGENT

### 7.3 典型问法

- `@zzz 这个群有哪些人`
- `@zzz 群里有谁`
- `@zzz 本群成员都有谁`
- `@zzz 这个群是什么情况`
- `@zzz 本群资料`

### 7.4 工具设计

#### 工具 1：`list_group_members`

用途：

- 获取当前群成员列表
- 支持关键词过滤
- 支持条数限制

输入建议：

- `session_id`
- `query`
- `limit`

限制建议：

- `session_id` 必须强制绑定当前会话
- `limit` 默认 20，最大 50
- 只返回公开字段，例如 `display_name`、`wxid`

数据来源：

- `wxbot` roster 接口
- `GET /plugins/wxbot/admin/roster/groups/{session_id}/members`

输出建议：

- `session_id`
- `session_name`
- `total`
- `members: [{ display_name, wxid }]`

#### 工具 2：`get_group_info`

用途：

- 获取当前群基础信息
- 获取群名、session_id、是否有 roster、最近成员事件摘要

输入建议：

- `session_id`

限制建议：

- 只能查当前群

数据来源：

- `GET /plugins/wxbot/admin/roster/groups`
- `member events`
- 当前会话配置表

输出建议：

- `session_id`
- `session_name`
- `source`
- `member_count`
- `recent_join_events`
- `recent_leave_events`

### 7.5 实现拆分

#### A. 新增 Agent Engine

建议新增模块：

- `app/agent/engine.py`
- `app/agent/tools/base.py`
- `app/agent/tools/wxbot.py`

核心职责：

- 构造带工具 schema 的 `ChatRequest`
- 执行 tool call
- 回填 tool result
- 最终产出自然语言答复

#### B. 工具执行循环

推荐流程：

1. 读取当前 session、当前消息、persona、memory
2. 根据当前会话可用工具构造 `tools`
3. 发起第一次 LLM 请求
4. 如果模型返回 `tool_calls`
5. 执行工具
6. 将工具结果作为 tool message 回填
7. 再次请求 LLM
8. 最多循环 2 到 4 次
9. 输出最终答复

建议限制：

- 单次最多 3 个 tool calls
- 单次 agent 最大执行时间 10 秒到 15 秒
- 工具结果单次最大字符数限制，例如 4000 到 8000

#### C. 路由识别

新增一个 Agent Intent Hook 或路由信号判断：

- 仅在微信群聊中生效
- 必须 `@机器人`
- 命中群信息关键词时才标记 `tools_available=true`
- Router 才可落到 `RouteType.AGENT`

Agent 意图关键词建议：

- 群成员
- 群里有谁
- 本群
- 大家
- 成员列表
- 谁在群里
- 这个群

### 7.6 一期验收标准

- `@机器人 这个群有哪些人` 能稳定返回真实成员摘要
- `@机器人 本群资料` 能返回当前群名与基础信息
- 没命中 Agent 意图时，仍按原有 LLM 逻辑回复
- `/` 命令不被 Agent 抢走
- 失败时能优雅降级，不影响主对话链路

## 8. 二期：实用版

### 8.1 目标

让 Agent 能查询“群里最近发生了什么”。

### 8.2 新增工具

#### 工具 3：`search_group_messages`

用途：

- 查询当前群最近消息
- 支持按关键词、成员、时间范围过滤

典型问法：

- `@zzz 刚才谁提到画图`
- `@zzz 今天谁说过 sub2api`
- `@zzz 最近谁在聊积分`

输入建议：

- `session_id`
- `query`
- `sender_name`
- `sender_wxid`
- `limit`
- `hours`

限制建议：

- 只能查当前会话
- 默认最近 24 小时或最近 100 条
- 返回裁剪后的文本摘要，不直接回灌整段原始大历史

数据来源：

- SDK `/ext/query/read`
- 或桥接后本地消息入站表

输出建议：

- 匹配条数
- 命中成员
- 最近样本消息列表

#### 工具 4：`get_group_public_facts`

用途：

- 汇总当前群的公开信息与当前平台状态

可包含：

- 今日发言人数
- 最近活跃 top
- 最近入群 / 退群
- 是否开启积分
- 是否开启审核
- 是否开启复读机
- 是否配置欢迎语

典型问法：

- `@zzz 这个群最近活跃吗`
- `@zzz 本群最近怎么样`
- `@zzz 这个群开了哪些功能`

### 8.3 二期附加目标

把部分插件状态作为工具暴露给 Agent：

- Credits
- Moderation
- Repeater
- Welcome

但仅做“读取状态”，不做写操作。

### 8.4 二期验收标准

- `@机器人 刚才谁提到xxx` 可基于真实消息回答
- `@机器人 本群最近谁最活跃` 可返回统计结果
- `@机器人 这个群开了哪些功能` 可读取插件状态
- 仍然保持短回复，不变成后台报表风格

## 9. 三期：完整版

### 9.1 目标

把 Agent 能力正式纳入插件体系与前端控制体系。

### 9.2 核心建设项

#### A. 工具注册机制插件化

目标：

- 每个插件都可声明自己的 Agent Tools
- 平台统一收集、注册、鉴权、执行

建议扩展插件接口：

- `get_agent_tools()`
- `execute_agent_tool(name, args, ctx)`

#### B. 前端可视化开关

按群 / 按会话配置：

- 是否启用 Agent
- 允许哪些工具
- 工具调用上限
- 是否允许读取历史消息
- 是否允许读取插件状态

#### C. 工具调用审计日志

建议记录：

- 触发时间
- session_id
- user_id
- tool_name
- tool_args
- tool_result 摘要
- trace_id
- 模型最终回复

#### D. 按群配置 Agent 能力范围

例如：

- A 群只允许查成员
- B 群允许查历史消息
- C 群允许查插件状态但不允许查成员清单

### 9.3 三期验收标准

- Agent 工具不再与 `wxbot` 强耦合
- 各插件可按统一协议暴露工具
- 前端可见、可控、可审计
- 可按群分配能力范围

## 10. 建议的数据与权限边界

### 10.1 会话边界

所有 Agent 工具默认只能操作：

- 当前 `tenant_id`
- 当前 `session_id`

禁止模型自行指定其他会话。

### 10.2 数据裁剪

必须限制：

- 成员列表最大返回数量
- 历史消息最大返回条数
- 工具结果最大字符数

### 10.3 权限分级

建议至少分为：

- 普通群成员可问公开群资料
- 管理员可问更完整统计信息
- 高风险能力不向普通成员开放

### 10.4 敏感信息

Agent 工具默认不应暴露：

- 私密记忆
- 非当前会话数据
- 内部配置密钥
- 未脱敏日志

## 11. 回复风格要求

Agent 虽然走工具，但最终回复仍必须服从现有风格体系：

- 群聊短回复优先
- persona skill 继续生效
- user memory 继续生效
- 不使用客服腔
- 不输出大段 JSON
- 不复述工具原始结果

工具只是“查数据”，不是直接把后台结果贴给用户。

## 12. 推荐实施顺序

建议按以下顺序推进：

### 第 1 批

- AgentCapabilityEngine
- 工具执行循环
- `list_group_members`
- `get_group_info`
- 群信息类路由识别

### 第 2 批

- `search_group_messages`
- `get_group_public_facts`
- 插件状态读取工具

### 第 3 批

- 插件化工具注册
- 前端 Agent 配置页
- 工具调用审计
- 按群权限控制

## 13. 代码落点建议

### 新增模块建议

- `app/agent/engine.py`
- `app/agent/registry.py`
- `app/agent/tools/base.py`
- `app/agent/tools/wxbot.py`

### 需要修改的现有模块

- `app/main.py`
  将 `RouteType.AGENT` 从普通 LLM 替换为真实 Agent Engine

- `app/router/*`
  增加 AGENT 路由信号

- `plugins/wxbot/*`
  提供 Agent 读取群资料所需服务接口

- `frontend`
  三期时增加 Agent 可视化配置页

## 14. 风险与注意事项

### 14.1 工具结果过大

如果成员太多、消息太多，容易导致上下文爆炸。

解决：

- 分页
- 限量
- 摘要化

### 14.2 Agent 抢走原有插件逻辑

如果路由优先级处理不好，会影响签到、积分、命令、审核等确定性能力。

解决：

- 命令优先
- 插件优先
- Agent 只吃“群事实类问法”

### 14.3 模型乱用工具

解决：

- 白名单工具
- 单轮调用上限
- 当前会话强绑定
- 参数校验

### 14.4 回复变成长文

解决：

- 继续复用现有群聊短回复约束
- Agent 工具输出结果必须摘要化

## 15. 最终结论

这套系统最适合的发展方向不是做一个“万能自主 Agent”，而是先做一个“会查当前群真实数据的群聊 Agent”。

一期重点解决“群成员 / 群资料”；
二期解决“最近消息 / 群公开事实 / 插件状态”；
三期再把工具体系正式插件化、可配置、可审计。

这样既能最大化复用当前架构，又能明显提升群聊互动质量，并且不会破坏现在已经稳定的命令、积分、审核、桥接和记忆链路。
